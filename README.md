# OpenCode v2 — Flutter Streaming Spike

Spike goal: prove that a Flutter app can send a prompt to an opencode v2 headless
instance and stream the AI response token-by-token, without any changes to opencode
itself.

**Status: confirmed working** — all findings were verified by live probing against
opencode v2.1.0.

## Architecture

```
opencode --service process  (always running, started by opencode on first launch)
│  REST API + SSE stream
│  URL + password auto-discovered from:
│    ~/.local/state/opencode/service.json
▼
relay/index.js  (Node.js, port 3000)
│  Session API — list / create / select / rename / fork / delete / compact,
│                switch model + agent, send prompts, interrupt execution
│  GET  /stream  — SSE fan-out of opencode's event stream
│  GET  /health  — liveness check
▼
flutter/lib/opencode_client.dart  (API layer)
   listSessions / createSession / renameSession / deleteSession / forkSession
   loadMessages / sendPrompt / interrupt / compactSession / setModel / setAgent
   eventStream() — typed SSE feed
▼
flutter/lib/main.dart  (Flutter app — web at :8080, or native Linux desktop)
   sidebar   — session list, new session, rename / fork / delete
   app bar   — model picker, agent picker, stop button, session menu
   transcript — user + assistant bubbles, reasoning, tool chips
   composer  — prompt the selected session
   session.text.delta events → text appended token-by-token
   session.execution.succeeded → transcript reloaded from opencode
```

### Key discovery

`opencode serve --stdio --port 0` starts the **web UI** (SPA), not the REST API.
Every path on that server returns `index.html`. The **real API** is the
`--service` background process. Its URL and per-launch random password are written
to `~/.local/state/opencode/service.json` on every launch. The relay reads this
file automatically — no manual configuration needed.

## Running as a Linux desktop app

A native window, launched straight from the terminal. **No APK, no Android
emulator, no Gradle** — `flutter run -d linux` compiles a small C++ runner plus
your Dart code and starts the resulting binary. Hot reload works exactly as on
web.

The Dart code is already desktop-safe: `fetch_client` ships an IO shim and
`lib/main.dart` guards it with `kIsWeb`, so desktop falls back to `http.Client`
over a plain TCP socket.

<sub>Last verified on Ubuntu 22.04, Flutter 3.24.3 (Dart 3.5.3), clang 14, CMake 3.22.</sub>

### 1. One-time system dependencies

```bash
sudo apt update
sudo apt install clang cmake ninja-build pkg-config libgtk-3-dev liblzma-dev \
                 libstdc++-12-dev
```

`flutter doctor` shows the Linux toolchain as ✗ until these are present.

**Why `libstdc++-12-dev` is in that list** — this is the non-obvious one. Clang
picks the newest GCC installation it finds (`/usr/lib/gcc/x86_64-linux-gnu/12`),
but Ubuntu often ships only the *runtime* `libstdc++6`, while the development
files (`libstdc++-11-dev`) belong to GCC 11. The mismatch produces two errors:

```
/usr/bin/ld: cannot find -lstdc++: No such file or directory
/usr/include/glib-2.0/glib/glib-typeof.h:39:10: fatal error: 'type_traits' file not found
```

Installing `libstdc++-12-dev` gives clang the headers *and* linker script for
the GCC version it actually targets. See *No-sudo workaround* under
[Troubleshooting](#troubleshooting) if you cannot install packages.

### 2. Enable the desktop target and generate the runner

Skip the `flutter create` line if `flutter/linux/` already exists — it is
generated once and then committed with the app.

```bash
export PATH="$HOME/flutter/bin:$PATH"
flutter config --enable-linux-desktop
cd flutter
flutter create --platforms=linux --project-name opencode_flutter_spike .
```

`--project-name` is required here: without it, `flutter create` derives the
project name from the directory name — `flutter` — and refuses with
`Invalid project name: 'flutter' - this will conflict with Flutter package
dependencies.`

If you would rather not risk `flutter create` touching existing generated files
(`README.md`, `.gitignore`, `web/index.html`), scaffold elsewhere and copy only
the new directory:

```bash
cd /tmp && flutter create --platforms=linux \
  --project-name opencode_flutter_spike linux_scaffold
cp -a /tmp/linux_scaffold/linux /path/to/opencode-spike/flutter/
```

The app's own name in `pubspec.yaml` is `opencode_flutter_spike`, so the
generated `linux/CMakeLists.txt` keeps the same binary name either way.

### 3. Run it

The relay must already be running (Terminal 1).

```bash
export PATH="$HOME/flutter/bin:$PATH"
cd /path/to/opencode-spike/flutter
flutter run -d linux
```

| key | action |
|-----|--------|
| `r` | hot reload |
| `R` | hot restart |
| `q` | quit |

### 4. Build a standalone binary (optional)

```bash
flutter build linux --debug      # → build/linux/x64/debug/bundle/
flutter build linux --release    # → build/linux/x64/release/bundle/
./build/linux/x64/debug/bundle/opencode_flutter_spike
```

The `bundle/` directory is self-contained: copy it anywhere and run the binary
without the Flutter toolchain.

### CORS is a web-only problem

On desktop there is no browser, therefore no origin, therefore no preflight —
`Cache-Control: no-cache` on `GET /stream` is simply sent. If the web target
still complains about CORS, the fix lives in the relay and requires a restart
(see [Troubleshooting](#troubleshooting)).

## Manual testing (without Flutter)

With the relay running, you can test every layer from the command line.

### 1. Health check

```bash
curl -s http://127.0.0.1:3000/health | jq
```

```json
{
  "relay": "ok",
  "opencode_url": "http://127.0.0.1:49374",
  "session_count": 3
}
```

### 2. Watch the event stream

Open a terminal and leave it running:

```bash
curl -sN http://127.0.0.1:3000/stream
```

### 3. Send a prompt

In another terminal:

```bash
curl -s -X POST http://127.0.0.1:3000/prompt \
  -H 'Content-Type: application/json' \
  -d '{"prompt": "Explain closures in one sentence"}'
```

```json
{ "status": "dispatched", "sessionId": "ses_ea7..." }
```

`/prompt` is the original single-session endpoint. It still works, but the app
uses the session-scoped endpoints below.

Watch Terminal 2 — you will see the response stream in:

```
data: {"type":"session.inbox.enqueued",...}
data: {"type":"session.execution.started",...}
data: {"type":"session.step.started","data":{"model":{"id":"glm-5.3",...},...},...}
data: {"type":"session.text.delta","data":{"delta":"A closure "},...}
data: {"type":"session.text.delta","data":{"delta":"is a function "},...}
...
data: {"type":"session.text.ended","data":{"text":"A closure is a function..."},...}
data: {"type":"session.execution.succeeded",...}
```

### 4. Target a specific model

```bash
curl -s -X POST http://127.0.0.1:3000/prompt \
  -H 'Content-Type: application/json' \
  -d '{
    "prompt":     "What is a monad?",
    "providerID": "camer-digital",
    "modelID":    "glm-5.3"
  }'
```

If `providerID` and `modelID` are omitted, opencode uses its last-used model.

> **How model selection actually works** — opencode's prompt endpoint does *not*
> accept a model. The relay therefore calls `POST /api/session/:id/model`
> (a "switch model" call) before sending the prompt. The same applies to
> `agent`.

## Session management API

These are the endpoints the Flutter app drives. All of them proxy opencode's
`/api/session*` routes, normalise the payloads (opencode wraps everything in
`{"data": …}`) and flatten message parts into `text` / `reasoning` / `tools`.

```bash
# list sessions (newest first) — id, title, model, cost, running
curl -s 'http://127.0.0.1:3000/sessions?limit=5' | jq

# create a session (optionally pick agent/model)
curl -s -X POST http://127.0.0.1:3000/sessions \
  -H 'Content-Type: application/json' \
  -d '{"title":"my task","agent":"assistant",
       "model":{"id":"glm-5.3","providerID":"camer-digital"}}' | jq

# prompt a specific session
curl -s -X POST http://127.0.0.1:3000/sessions/<id>/prompt \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Explain closures"}' | jq

# transcript (oldest first, normalised)
curl -s http://127.0.0.1:3000/sessions/<id>/messages | jq

# stop a running execution
curl -s -X POST http://127.0.0.1:3000/sessions/<id>/interrupt | jq

# rename / fork / compact / delete
curl -s -X PATCH  http://127.0.0.1:3000/sessions/<id> -d '{"title":"renamed"}'
curl -s -X POST   http://127.0.0.1:3000/sessions/<id>/fork    -d '{}'
curl -s -X POST   http://127.0.0.1:3000/sessions/<id>/compact -d '{}'
curl -s -X DELETE http://127.0.0.1:3000/sessions/<id>

# switch model / agent without prompting
curl -s -X POST http://127.0.0.1:3000/sessions/<id>/model \
  -d '{"providerID":"opencode","modelID":"minimax-m3.1-flash-free"}'
curl -s -X POST http://127.0.0.1:3000/sessions/<id>/agent -d '{"agent":"assistant"}'

# metadata for the pickers
curl -s http://127.0.0.1:3000/models   | jq '{default, count:(.models|length)}'
curl -s http://127.0.0.1:3000/agents   | jq '.agents[] | {id,name}'
curl -s http://127.0.0.1:3000/commands | jq '.commands[0:3]'
curl -s http://127.0.0.1:3000/active   | jq
```

| method | path | purpose |
|--------|------|---------|
| `GET` | `/sessions` | list, `?limit=&search=&archived=` |
| `POST` | `/sessions` | create `{title?, agent?, model?}` |
| `GET` | `/sessions/:id` | one session |
| `PATCH` | `/sessions/:id` | rename `{title}` |
| `DELETE` | `/sessions/:id` | delete |
| `GET` | `/sessions/:id/messages` | normalised transcript |
| `POST` | `/sessions/:id/prompt` | prompt `{prompt\|text}` |
| `POST` | `/sessions/:id/command` | slash-command `{name, text?}` |
| `POST` | `/sessions/:id/interrupt` | stop execution |
| `POST` | `/sessions/:id/fork` | branch transcript |
| `POST` | `/sessions/:id/compact` | compact context |
| `POST` | `/sessions/:id/model` | switch model `{providerID, modelID}` |
| `POST` | `/sessions/:id/agent` | switch agent `{agent}` |
| `GET` | `/models` `/agents` `/commands` `/active` | picker data |

Upstream client errors are passed through: a deleted session returns `404`,
a malformed payload `400`. Everything else becomes `502` with the opencode
error text.

## SSE event lifecycle

Every AI response follows this sequence of event types on `/stream`:

| # | event type | meaning |
|---|-----------|---------|
| 1 | `session.inbox.enqueued` | prompt accepted |
| 2 | `session.execution.started` | opencode starting work |
| 3 | `session.instructions.updated` | system prompt built |
| 4 | `session.inbox.delivered` | prompt handed to model runner |
| 5 | `session.step.started` | model inference begins; contains model id |
| 6 | `session.text.started` | text stream opening |
| 7 | `session.text.delta` ×N | **streaming token** — `data.delta` is the text chunk |
| 8 | `session.text.ended` | full text in `data.text`; used as safety-net |
| 9 | `session.step.streamed` | stream closed |
| 10 | `session.step.ended` | finish reason + token counts |
| 11 | `session.usage.updated` | cumulative cost/tokens for session |
| 12 | `session.execution.succeeded` | all done |

Session-management events keep the sidebar in sync even when the change came
from another client:

| event type | payload |
|-----------|---------|
| `session.created` | `{sessionID, title, projectID, location}` |
| `session.renamed` | `{sessionID, title}` |
| `session.deleted` | `{sessionID}` |
| `session.model.selected` | `{sessionID, model:{id, providerID, variant}}` |
| `session.agent.selected` | `{sessionID, agent}` |
| `session.execution.interrupted` | `{sessionID}` |

Every session-scoped event carries `data.sessionID`, so a client can ignore
turns belonging to other sessions.

The Flutter app listens for `session.text.delta` to build text incrementally,
uses `session.text.ended` as a ground-truth check, and reloads the transcript
from `/sessions/:id/messages` when the turn finishes.

## How the Flutter app works

Two files:

- `flutter/lib/opencode_client.dart` — no widget imports, unit-testable
- `flutter/lib/main.dart` — everything you see on screen

### `OpenCodeEvent` — typed event model

Maps the raw `"type"` string from every SSE JSON frame to a Dart enum.
Provides typed accessors: `.textDelta`, `.fullText`, `.tokens`, `.sessionId`,
`.title`, `.model`, `.agent`.

### `SessionInfo` / `ChatMessage` / `ToolCall` / `ModelInfo` / `AgentInfo`

Plain data classes mirroring the relay's normalised JSON. `SessionInfo` knows
how to label untitled sessions ("New session") and untitled models.

### `OpenCodeRelayClient` — HTTP + SSE logic

Every session operation the UI exposes:

```dart
listSessions()      createSession()   renameSession()  deleteSession()
loadMessages()      sendPrompt()      interrupt()      compactSession()
forkSession()       setModel()        setAgent()       runCommand()
loadModels()        loadAgents()      health()         eventStream()
```

The HTTP client is chosen per platform:

```dart
final http.Client _http =
    kIsWeb ? FetchClient(mode: RequestMode.cors) : http.Client();
```

`FetchClient` is needed on web because it exposes the browser Fetch API's
streaming body reads (plain `http` cannot stream a response there). On desktop
and mobile the standard `http.Client` is used, so no CORS or preflight applies.

The stream handles partial SSE frames across HTTP chunks by buffering on `\n\n`
and reconnects automatically with a 2-second back-off.

### `OpenCodeSpikePage` — Flutter UI

- **Sidebar** (permanent ≥ 900 px wide, drawer below that): session list with
  relative timestamps, model names and a running dot; `+` creates a session,
  refresh re-lists, and each row's menu offers rename / fork / delete.
- **App bar**: current title + live status, model picker, agent picker, a red
  stop button while a turn is running, and a session menu (rename / fork /
  compact / delete).
- **Transcript**: user messages right-aligned, assistant messages left with
  selectable monospace text, a collapsible `reasoning` block, tool chips
  coloured by status, and a `$cost` footer. opencode's `idle` markers are
  hidden; `model → …`, `agent → …` and `context compacted` breadcrumbs remain.
- **Composer**: sends into the selected session (creating one if none exists).
  `session.text.delta` appends to a live buffer; `session.text.ended` replaces
  it with the full text; `session.execution.succeeded` reloads the transcript
  from opencode so the persisted view always wins over the streamed view.
- **Reactive list**: `session.created` / `renamed` / `deleted` events trigger a
  debounced re-list, so changes made from the TUI or another app show up here.

### Tests

`flutter/test/widget_test.dart` pins the JSON → model mapping using payloads
captured live from opencode v2.1.0 — no relay or opencode needed:

```bash

```

## OPENCODE_DB and state paths

| path | contents |
|------|---------|
| `~/.local/share/opencode/opencode.db` | SQLite — all sessions, messages, costs |
| `~/.local/state/opencode/service.json` | **per-launch** API URL, PID, password |
| `~/.local/state/opencode/model.json` | last-used model |
| `~/.config/opencode/opencode.json` | user config (providers, MCP, agents) |

### Per-launch password

opencode generates a random password on every service start and writes it to
`service.json`. The relay reads this file at boot — no manual credential passing
is ever needed.

Override with a static password by creating `~/.config/opencode/service.json`:
```json
{ "password": "your-static-password" }
```

### Isolating test runs (avoids SQLite lock contention)

```bash
d=$(mktemp -d)
XDG_DATA_HOME="$d/share" XDG_STATE_HOME="$d/state" opencode serve
```

## Troubleshooting

| symptom | cause | fix |
|---------|-------|-----|
| `service.json not found` | opencode never launched | run `opencode` once |
| `opencode service not running` | service crashed | re-launch opencode |
| `EADDRINUSE :3000` | relay already running | `scripts/relay.sh` kills stale process |
| relay starts but no events | service.json has stale PID | re-launch opencode, re-run relay |
| Flutter shows `stream error` | relay not up when app started | start relay first |
| `Request header field cache-control is not allowed by Access-Control-Allow-Headers` | browser preflight rejected because the relay's allow-list omitted `Cache-Control` | update `relay/index.js` (it now echoes `Access-Control-Request-Headers`) **and restart the relay** |
| Chrome CORS error, generally | relay not sending CORS headers | relay has global CORS middleware — check it is running |
| `Invalid project name: 'flutter'` | `flutter create .` derives the name from the folder, which is called `flutter` | add `--project-name opencode_flutter_spike` |
| `/usr/bin/ld: cannot find -lstdc++` | clang targets GCC 12, but only `libstdc++-11-dev` is installed | `sudo apt install libstdc++-12-dev` |
| `'type_traits' file not found` | same GCC 11/12 mismatch — C++ headers for GCC 12 absent | same fix, `libstdc++-12-dev` |
| Only last token visible in curl | expected — `curl -sN /stream` shows all fragments live | use `watch_deltas.js` or the Flutter app |

### No-sudo workaround for the clang/GCC 11/12 mismatch

If you cannot install `libstdc++-12-dev`, point clang at the GCC 11 files
instead of the (incomplete) GCC 12 install:

```bash
export CXXFLAGS="-isystem /usr/include/c++/11 \
  -isystem /usr/include/x86_64-linux-gnu/c++/11 \
  -isystem /usr/include/c++/11/backward"
export LDFLAGS="-L/usr/lib/gcc/x86_64-linux-gnu/11"
```

Then build/run as usual. CMake captures these flags on its **first** configure,
so run `flutter clean` after adding or changing them — otherwise the cached
values are reused and the same error persists. Note that clang 14 has no
`--gcc-install-dir` flag (clang 15+ only), which is why header/linker paths are
passed explicitly.
